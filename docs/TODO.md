- [ ] **Laravel API — три ступени, спешить не обязательно.**
  1. **Без базы вообще.** Справочник константами в PHP, заказ не сохраняется: сервер валидирует,
     считает цену и возвращает номер. Этого хватит, чтобы фронт переключился с `httpbin` на
     настоящий бэк и всплыли CORS и формат ошибок 422. ~полчаса.
  2. **SQLite.** Ноль настройки, в Laravel 11+ по умолчанию. Миграции, Eloquent, сидеры —
     знакомо по `my-buy-list`.
  3. **Postgres.** Когда захочется посмотреть на реальный переезд (меняется строка в `.env`
     плюс прогнать миграции; ломается обычно пара мест с датами и автоинкрементами).

  Минимум на первый заход — только `POST /api/orders`:
  маршрут в `routes/api.php`, `FormRequest` с валидацией (`in:S,M,L` вместо `exists`, пока нет
  таблиц), ответ `{ "orderId": "...", "price": ... }`, CORS на `http://localhost:5173`
  в `config/cors.php`.
  ⚠️ **Цену считает сервер**, клиент её не присылает — см. первый пункт в «Сейчас».
  На фронте меняется **один файл** `order.api.ts`. Если контракт собран верно — больше нигде.
  Это и есть проверка слоя API.

- [ ] **Docker — свой `docker-compose.yml`, не Sail.**
  Sail удобен, но генерирует готовое и прячет механику; цель здесь — разобраться, поэтому пишем
  руками. Теория и команды: `KNOWLEDGE/cheatsheets/docker.md`.
  Два сервиса: `app` (PHP + `artisan serve`, без nginx на первом заходе) и `db` (Postgres).

  См. `KNOWLEDGE/REMINDERS.md`.

- [ ] **Второй Mac mini — что туда можно вынести.**
  Критерий не «часто ли меняется», а **нужен ли сервису доступ к твоим файлам**:
  - **база** общается только через порт → выносится легко (`DB_HOST=192.168.x.x` в `.env`);
  - **Laravel** нужен bind mount кода → по сети (SMB/NFS) работает отвратительно, держать локально.

  Элегантный способ, если выносить несколько сервисов — удалённый контекст:
  `docker context create mini --docker "host=ssh://user@192.168.1.50"`, дальше команды те же.
  **Но выигрыш невелик**, пока Laravel крутится локально: виртуалка Docker Desktop всё равно
  запущена, а она и есть основной едок. Настоящая выгода — если на основной машине не останется
  контейнеров вообще.
  Интереснее другое применение: держать на втором маке то, что должно работать **постоянно** —
  стенд с задеплоенной пиццей, чтобы смотреть «как в бою», в том числе с телефона по
  `http://192.168.x.x:8000`.

- [ ] **Автодеплой на второй мак по push.**
  **Self-hosted runner** GitHub Actions: ставится на второй мак, сам подключается к GitHub
  наружу — работает за роутером, без белого IP и проброса портов.

  ```yaml
  on: { push: { branches: [main] } }
  jobs:
    deploy:
      runs-on: self-hosted
      steps:
        - uses: actions/checkout@v4
        - run: docker compose up -d --build
  ```

  ⚠️ **Только для приватного репозитория.** На публичном любой pull request выполнит свой код
  на твоей машине. Проверить видимость `wizard-lab` перед настройкой.
  Попутно разберёшься с GitHub Actions — на работе это пригодится больше, чем сам докер.
  Проще вариант без Actions: cron на втором маке с `git pull` и пересборкой.
  Доступ из интернета (если понадобится) — Cloudflare Tunnel: бесплатен, работает за NAT,
  адрес постоянный. У ngrok в бесплатном тарифе адрес меняется при каждом запуске.
